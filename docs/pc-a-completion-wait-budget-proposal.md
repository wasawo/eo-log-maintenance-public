# PC-Aの毎時完了確認に対する上限（判断案）

状態: 利用者判断待ち。確認task/待機記録/manifest変更は未実装。
根拠: C-24はPC-AがPC-B完了を毎時確認し、無期限に待たないことを要求する。月次時刻は[承認済み](task-monthly-schedule-policy-proposal.md)。

## 推奨する確認予算

PC-A自身の同期が安全に完了し、同じ対象period/log種別のPC-B待ちと判断した最初の適格観測から最大24時間とする。
初回確認に加え1時間より短く詰めずに確認し、24時間到達まで（初回を含め最大25回）。上限後は予約を増やさず「保留・要確認」を可視化する。
時計・残予算・対象identityを検証できない場合も停止する。PC再起動やログオンし直しで予算を黙って延長しない。
ログオフ/停止中の確認を成功扱いせず、実行機会がなければ25回未満でも期限で保留する設計。期限の永続化/時計の資格は別途実装・検証する。

各確認で最新manifestの一意性・範囲/内容・Drive等を再検証し、古いsuccessへ後退しない。
ただし破損/曖昧/読取不明等を「待てばよい」と扱わず、その安全gateで停止する。
待ち時間の間ずっとmutexを保持しない。実行する各確認の必要区間で取得し、上限や取得失敗の安全条件を緩めない。

## 期限後にしないこと

- PC-Bや旧running manifestをfailure/successへ書き換えない。
- 未確認をskip/successとしてarchiveへ進めず、旧successで代用しない。
- stale lockを削除/回復したり、unknown uploadを自動retryしたりしない。
- この24時間を既存の鮮度24時間、未来許容、mutex待機60秒やleaseへ読み替えない。別の運用予算として記録する。

再開は明示的な操作と新しい安全検証を必要とする方向。再開方式、記録schema/保存、通知方法、正式task統合はこの承認だけでは完成扱いしない。

## 判断してほしいこと

最大24時間（毎時、初回含め最大25回）で保留・要確認とするか、希望する時間/回数上限を指定する。
承認しても実task・待機・本番archiveは開始しない。
