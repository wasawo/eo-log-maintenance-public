# PowerShell・Python 責務分担／連携契約書

- 状態：Phase 1 契約案（レビュー待ち）
- バージョン：1.0
- 対象範囲：PowerShell による処理制御と Python による Google Drive アダプター
- 破壊的操作：**未実装。本契約により禁止する**
- 機械可読スキーマ：
  - [リクエストスキーマ](../../contracts/drive-request.schema.json)
  - [レスポンススキーマ](../../contracts/drive-response.schema.json)

## 1. 契約の基本原則

1. 処理全体を制御する唯一の主体は PowerShell とする。ワークフローを続行できるかどうかを判断し、安全確認をすべて管理する。
2. Python は Google Drive API の限定的なアダプターとする。明示的に要求された Drive 操作だけを実行し、その結果を返す。
3. Python のレスポンスが `success: true` であっても、意味するのは要求されたアダプター操作の成功だけである。ローカルファイルや Drive ファイルの削除を許可するものではない。
4. 結果が不正、欠落、矛盾、期限切れ、タイムアウト、または検証不能の場合、現在のワークフローを停止する。呼び出し元はフェイルクローズで動作する。
5. Pythonアダプターは1回のAPI試行だけを行い、自動再試行を一切行わない。再試行の分類・回数・待機時間はPowerShellだけが管理する。アップロード結果が不明な場合は、再アップロード前にDrive上の状態を照合する。
6. 契約はバージョン管理する。未知のスキーマバージョン、操作名、フィールド、エラーコードは拒否する。
7. 認証情報、アクセストークン、リフレッシュトークン、認証ヘッダー、秘密情報を含むレスポンス本文を JSON 出力やログに記録してはならない。

## 2. 責務分担

### PowerShell — 処理制御とローカル側の安全管理

PowerShell が担当する事項：

- PC ごとの設定および役割（PC-A／PC-B）の読み込みと検証。
- ローカルファイルの列挙と、処理対象となるログ期間の選定。
- パス、許可ルート、ファイル名、コピー元／コピー先の分離、PC の役割に応じた制約の検証。
- ローカルファイルの SHA-256 計算とローカルコピーの検証。
- PC-A／PC-B のマニフェストの作成、読み込み、検証。実行識別子、期間、ログ種別、状態、鮮度を含む。
- 両 PC の処理完了、クラウド上の確認、アーカイブ検証に関するすべての安全条件が満たされたかどうかの判断。
- 子プロセスとしての Python の起動、タイムアウト管理、標準出力／標準エラーの取得、終了コードと JSON の検証、`request_id` の照合。
- Dry Run、運用者承認、実行ロック、構造化運用ログ、タスクスケジューラからの起動の管理。
- 初期実装ではローカル元ファイル削除・Drive削除のコード、操作、設定を持たせない。将来の削除機能は別途設計・レビュー・承認が必要であり、本契約の範囲外とする。
- 一時的エラーに対する再試行を一元管理する。初回を含む最大4回、待機は1分・5分・15分とする。

子プロセスの異常終了、タイムアウト、不正な出力、リクエスト ID の不一致、未知のスキーマバージョン、想定外の出力はすべて失敗として扱う。Google Drive for desktop のローカルフォルダーにファイルが存在することだけを根拠に、成功と判断してはならない。

### Python — Google Drive アダプター

Python が担当する事項：

- 承認済みのローカル認証情報ストアを使用した Google OAuth 認証情報の読み込みと更新。
- 第 3 章に列挙した操作に限定した Google Drive API 呼び出し。
- API のレスポンスと例外の、 第 6 章で定義する安定したエラーコードへの変換。
- 受理したリクエストごとに、契約に適合する JSON レスポンスを 1 件返すこと。
- リクエストを検証したうえで、呼び出し元が指定したステージングパスにのみダウンロードすること。コピーの検証と最終配置は、その後 PowerShell が行う。
- APIを1回だけ試行し、その結果を終了コードとJSONで返す。Python内部の再試行、バックオフ、ジッター、およびHTTPクライアント／ライブラリの暗黙の再試行は禁止する。

Python が行ってはならない事項：

- PC-A／PC-B の処理完了条件が満たされたと判断すること。
- マニフェストをアーカイブや削除の許可として解釈すること。
- ローカルファイルまたは Google Drive ファイルを削除すること。
- 競合を解決するために既存の運用ファイルを名前変更、上書き、削除すること。
- コマンドライン引数や設定値によって破壊的な動作を有効化すること。
- Drive for desktop のローカルフォルダーにファイルが存在することを、クラウドへのアップロード完了の証明として扱うこと。

### Phase 1 で禁止する事項

このフェーズで作成するのはドキュメントとスキーマのみである。実行時の処理制御、アップロード、ダウンロード、アーカイブ、削除の実装は行わない。リクエストスキーマにも削除操作を定義しない。

## 3. Python が受け付ける操作

操作名は大文字・小文字を区別する。次の 4 種類だけを有効とする。

| 操作 | 必須パラメーター | `dry_run=false` の場合の効果 | 制約 |
|---|---|---|---|
| `list_files` | `parent_id` | クラウド上の Drive メタデータを検索する | 読み取り専用。ページングを明示的に扱う |
| `get_file_metadata` | `file_id` | クラウド上の Drive メタデータを取得する | 読み取り専用 |
| `upload_file` | `local_path`、`parent_id`、`file_name`、`expected_sha256` | 新規ファイルをアップロードする | 内容の異なる既存ファイルを上書きしない。重複候補を一意に判定できない場合は失敗 |
| `download_file` | `file_id`、`staging_path` | ステージング先にファイルをダウンロードする | 最終アーカイブ先には書き込まない。呼び出し元が内容を検証する |

`dry_run=true` の場合、アダプターは Drive を変更せず、ダウンロードしたファイルの内容も書き込んではならない。リクエストを検証し、変更を行わない計画または結果を返す。

OSD-04は2026-10-24に[A方針](../decisions/dry-run-side-effect-policy-proposal.md)を利用者承認済み。Dry Runではアプリによる意図的ファイル書込みを行わず、検証済み入力の読取りと機密除去済み標準ストリーム出力に限る。運用manifest/report/lock/確認予算の更新、bootstrap、ACL変更、credential refresh/store、download bytes取得を行わない。準備不足・不明状態は作成・修復せず停止する。

§4/8/9の一時request/responseファイル作成・ファイルへの診断記録・cleanupは通常実行の手順であり、Dry Runでは適用しない。Dry Runには安全なファイル不要のIPC経路が必要で、成立しなければ停止する。stdoutのJSON 1件、stderr分離、秘密除去は維持する。OSの自動atime等を含めた物理書込みzeroの保証ではない。Bの限定書込みは未採用。OSD-05未解決中のlive Drive接続、IPC契約全体の承認、runtime実装や受け入れをこの方針承認から推定しない。

`upload_file` は、アップロード直前にローカルファイルの SHA-256 を `expected_sha256` と照合しなければならない。APIからクラウド側SHA-256を取得できない場合、PowerShellはAPI経由でファイルをダウンロードしてSHA-256を計算する。ダウンロード検証ができない、識別が曖昧、サイズ／ハッシュ不一致の場合は失敗として元ファイルを保持し、期間を未完了とする。初期実装に削除処理は含めない。

ID や名前による検索結果が曖昧な場合、アダプターは別のファイルを暗黙に選択してはならない。一覧およびメタデータのレスポンスには、取得できる場合、安定した Drive ファイル ID、名前、MIME タイプ、サイズ、更新日時、親 ID を含める。チェックサムは API が実際に返した場合に限り含める。

## 4. リクエスト契約

Python CLI へのリクエストは、UTF-8 の JSON ファイル、またはコマンドライン長と引用符処理を安全に管理できる場合に限り単一の JSON 引数で渡す。**推奨方式：** 実行ごとの一時ディレクトリにアクセス制限を設定した UTF-8 リクエストファイルを作成し、処理終了後に削除する。認証情報をリクエストに含めてはならない。

必須エンベロープ：

| フィールド | 型 | 規則 |
|---|---|---|
| `schema_version` | 文字列 | `1.0` と一致すること |
| `request_id` | 文字列 | UUID。レスポンスに同じ値をそのまま返すこと |
| `operation` | 文字列 | 第 3 章に定義した 4 操作のいずれか |
| `dry_run` | 真偽値 | 必須。呼び出し元が明示的に指定すること |
| `parameters` | オブジェクト | 操作別に許可されたフィールドのみを含むこと |

未知のフィールドは拒否する。操作に必要なパラメーターはすべて存在し、空であってはならない。Windows 専用の実行環境であるため、パスは絶対 Windows パスとする。呼び出し元は設定済みの許可ルートと照合し、Python も不正なパス構文を拒否しなければならない。パスの指定は、ファイルの削除や上書きの許可を意味しない。

読み取り専用リクエストの例：

```json
{
  "schema_version": "1.0",
  "request_id": "8c7e5db8-08f4-4c9e-a6b2-5b45c1aaf031",
  "operation": "get_file_metadata",
  "dry_run": true,
  "parameters": {
    "file_id": "drive-file-id"
  }
}
```

リクエスト／レスポンスのスキーマファイルを規範とする。本書の例は説明用である。

## 5. レスポンス契約

Python は標準出力に、UTF-8 の JSON オブジェクトを 1 件だけ出力し、その末尾に改行を付ける。診断情報は標準エラーに出力する。標準出力にバナー、進捗表示、トレースバック、その他 JSON 以外の文字列を出してはならない。

必須レスポンスフィールド：

| フィールド | 型 | 規則 |
|---|---|---|
| `schema_version` | 文字列 | `1.0` と一致すること |
| `request_id` | 文字列 | リクエストと完全一致すること |
| `success` | 真偽値 | 操作結果のみを表し、削除の許可を意味しない |
| `operation` | 文字列 | リクエストの操作と一致すること |
| `result` | オブジェクトまたは null | 成功時のみオブジェクトとする |
| `error` | オブジェクトまたは null | 失敗時のみオブジェクトとする |

成功レスポンスは `success: true`、オブジェクト型の `result`、`error: null` とする。失敗レスポンスは `success: false`、`result: null`、および `code`、`message`、`retryable` を含む `error` オブジェクトとする。エラーメッセージはログに記録しても安全な内容とし、認証情報や機密性のある API ペイロードを露出させてはならない。

成功レスポンスの例：

```json
{
  "schema_version": "1.0",
  "request_id": "8c7e5db8-08f4-4c9e-a6b2-5b45c1aaf031",
  "operation": "get_file_metadata",
  "success": true,
  "result": {
    "file_id": "drive-file-id",
    "name": "example.log",
    "size": 1234,
    "mime_type": "text/plain",
    "sha256": null,
    "cloud_content_verified": false
  },
  "error": null
}
```

この例の `cloud_content_verified` は、メタデータ取得だけでは内容を検証できないため、明示的に `false` としている。実装が該当する検証を実行し、その方法を文書化した場合に限り `true` を許可する。

失敗レスポンスの例：

```json
{
  "schema_version": "1.0",
  "request_id": "8c7e5db8-08f4-4c9e-a6b2-5b45c1aaf031",
  "operation": "get_file_metadata",
  "success": false,
  "result": null,
  "error": {
    "code": "DRIVE_PERMISSION_DENIED",
    "message": "要求された Drive リソースにアクセスできません。",
    "retryable": false
  }
}
```

## 6. 終了コードとエラー対応

プロセス終了コードと JSON レスポンスの内容は一致しなければならない。有効なレスポンスを生成できない場合、PowerShell は診断目的で終了コードと標準エラーを参照するが、操作の成功を推定してはならない。

| 終了コード | 固定エラーコード | 意味 | 再試行方針 |
|---:|---|---|---|
| `0` | — | リクエスト成功。JSON の `success: true` が必須 | 再試行しない |
| `2` | `INVALID_REQUEST` | JSON 不正、必須フィールド欠落／不正、未対応操作またはスキーマバージョン | 再試行しない |
| `3` | `AUTHENTICATION_FAILED` | 認証情報の欠落・不正、または更新失敗 | 認証情報を修正するまで自動再試行しない |
| `4` | `DRIVE_PERMISSION_DENIED` | Drive の権限またはスコープ不足 | 再試行しない |
| `5` | `DRIVE_RESOURCE_NOT_FOUND` | 指定された Drive ID／リソースが存在しない、または参照できない | 再試行しない。呼び出し元が識別情報を再確認する |
| `6` | `DRIVE_TRANSIENT_FAILURE` | 1回のAPI試行で発生したネットワーク障害、HTTP 429、対象HTTP 5xxなどの一時的障害 | PowerShellが再試行可否を判定する。Pythonは内部再試行しない |
| `7` | `VERIFICATION_FAILED` | サイズ、ハッシュ、内容、または識別情報の検証失敗 | データを上書きする可能性のある再試行は禁止。コピー元を保持する |
| `8` | `INTERNAL_ERROR` | 予期しないアプリケーションエラー | 原則として自動再試行しない |
| `9` | `OPERATION_TIMEOUT` | アダプター側の処理タイムアウト | フェイルクローズ。処理状態を照合するまで再試行しない |
| `10` | `CONFLICT_OR_AMBIGUOUS` | 候補の複数存在、名前衝突、安全に上書きできるか不明 | 再試行しない。安全な競合解決が必要 |

親プロセスの PowerShell も実時間のタイムアウトを設定する。PowerShell が子プロセスを強制終了した場合、有効なレスポンスは得られていないものとし、呼び出し元側のタイムアウトとして記録して処理を停止する。アップロード後のタイムアウトやレスポンス喪失では、リモート操作の結果が不明な場合があるため、再試行前にクラウド側の状態を照合する。

終了コードとレスポンスが矛盾する場合（例：終了コード 0 なのに `success: false`、または終了コードが 0 以外なのに `success: true`）、呼び出しを失敗として扱い、結果を利用しない。JSON の欠落、複数 JSON オブジェクト、UTF-8 不正、JSON 構文エラー、`request_id` の不一致、`operation` の不一致、未知のレスポンススキーマ／エラーコードも、すべてフェイルクローズとする。

## 7. 再試行と冪等性

- 再試行の唯一の所有者はPowerShellとする。初回を含む最大4回とし、失敗後の待機は1分・5分・15分とする。ジッター付き指数バックオフは使用しない。
- 認証、権限、リクエスト不正、検証失敗、曖昧性のエラーは、根本原因を解消せずに再試行しない。
- Pythonは一覧取得・メタデータ取得を含むすべての操作を1回だけ試行する。PowerShellは `retryable` と固定エラーコードを確認して一時的エラーだけを再試行する。認証・権限・リクエスト不正・検証失敗・競合は再試行しない。
- アップロード結果が不明な場合は、同じアップロードを繰り返す前にDriveの一覧・メタデータを照合する。親ID・名前・サイズ・取得可能なチェックサム等で対象を一意に特定できなければ停止する。
- ダウンロードを再試行する場合、PowerShellは新規または空のステージングファイルを使用し、最終配置前にサイズとSHA-256を検証する。HTTPクライアントの暗黙の再試行が無効であることを設定とテストで確認する。
- 内容の異なる既存ファイルを上書きする形で再試行してはならない。
- 再試行回数の上限到達は失敗とし、成功扱いのスキップにしてはならない。

## 8. PowerShell からの呼び出し手順

1. ローカル設定、PC の役割、パス、実行状態、操作許可リストを検証する。
2. 新しい UUID の `request_id` と明示的な `dry_run` 値を含むリクエストを作成する。
3. 実行単位の一時領域に UTF-8 JSON のリクエストファイルを書き込む。
4. 設定済みの Python インタープリターを絶対パスで起動し、タイムアウトを適用する。
5. 標準出力と標準エラーを分離して取得し、レスポンス JSON がちょうど 1 件であることを確認して解析する。
6. レスポンススキーマ、リクエスト ID、操作名、終了コードとの整合性、操作固有の結果フィールドを検証する。
7. 必要に応じて、Drive の識別情報／メタデータとダウンロード済みデータを独立して検証する。
8. 関連する安全条件がすべて満たされた場合に限り続行する。それ以外は停止し、コピー元データを保持する。
9. マスキング済みの診断結果を記録した後、この呼び出しが作成した一時リクエスト／レスポンスファイルだけを削除する。

Python の成功レスポンスを根拠に、PowerShell が行うマニフェスト、両 PC の完了状態、PC 役割、チェックサム、アーカイブ検証、明示的な運用者承認の確認を省略してはならない。

## 9. ログとセキュリティ

- ログには UTC 時刻、実行 ID、リクエスト ID、操作名、処理時間、終了コード、固定エラーコード、機密情報を除去した結果概要を含める。
- OAuth トークン、リフレッシュトークン、クライアントシークレット、認証ヘッダー、機密性のある認証情報パス、未加工の API エラー本文を記録しない。
- ログ本文をリクエスト／レスポンス JSON に含めない。
- 一時リクエスト／レスポンスファイルへのアクセスを実行ユーザーに制限し、当該実行が作成したファイルを後処理で削除する。
- 必要最小限の Google Drive スコープを使用し、実装前に対象フォルダーへのアクセスを検証する。
- マニフェストとクラウドメタデータは信頼できない入力として扱い、スキーマ、識別情報、期間、ログ種別、状態、タイムスタンプ／鮮度、チェックサムを検証する。

## 10. Phase 1 の受け入れ条件

- [x] PowerShell と Python の責務を分離した。
- [x] リクエスト／レスポンスの JSON スキーマをバージョン管理し、機械可読にした。
- [x] 対応操作から削除操作を除外した。
- [x] 終了コードと固定エラーコードを定義した。
- [x] タイムアウト、不正出力、リクエスト照合、PowerShell一元管理の再試行、冪等性、フェイルクローズ動作を定義した。
- [x] このフェーズはドキュメント／スキーマのみとし、実行時の破壊的操作を実装していない。
- [ ] 運用者による契約レビューと承認。
- [ ] 後続フェーズでスキーマ検証テストおよび PowerShell／Python 間の契約結合テストを追加。

Phase 1 はドキュメント案として完成している。削除機能を有効化する許可でも、本システムを本番運用可能と判断する根拠でもない。
