# 移動記録v1の形式・保存・参照検査

更新日: 2026-10-28。根拠は[正式設計](log-move-design.md)§9〜16と[実装計画](../development/implementation-workflow.md)のT0/T4。実装再開指示の範囲で、既存の記録案をコードで扱える形式にした。

## 今回実装したもの

[move-record-v1.schema.json](../../contracts/move-record-v1.schema.json)で外形を定め、[MoveJournal.py](../../Common/MoveJournal.py)で型・参照・判定の整合、保存と読戻しを実装する。manifest v1とDrive IPCのschemaは変更しない。レコードを読めることと、実状態の確認・操作権限を得ることは区別する。

1イベントを1つのUTF-8 JSONとして保存する。保存先は、呼出し側が資格を確認した各PCの`maintenanceLocal`内の専用記録rootを想定し、その直下の`<record_id>.json`だけを扱う。rootの生成・本番配置はまだ接続しない。run/move/attemptのUUIDを別々に保持するため、ファイル名に実パスやクラウドIDを使わない。

既存の非上書き公開処理を再利用する。同じID・同じbytesの再保存は許可し、同じID・異なるbytesは拒否する。更新、削除、自動清掃、保存期間経過による証拠破棄は提供しない。保持期間と運用時の容量方針は引き続き別の判断事項である。

## 外形と対象の識別

全イベントに、`record_version=1`、`record_id/run_id/move_id/attempt_id`、`event_kind`、`route/machine_id/log_type`、`observed_at_utc/recorded_at_utc`、`prior_record_refs`、`event_data`を必須とする。未知key、重複JSON key、非整数の数値表現、無効日付、余分なBOM等を拒否する。UTC日時の小数部は文字列として保持し、マイクロ秒へ丸めない。日時の形式が正しくても時計の信頼性を証明した扱いにはしない。

経路は`local_to_cloud`と`cloud_to_archive`。後者のPC-Bを拒否する。ローカル対象はPC、設定rootキー、canonical相対path、volume番号と128-bit File IDで表す。cloud対象は設定rootキー、file ID、parent ID、name、取得できた場合のversion文字列で表す。versionがあるだけで条件付き削除を認可しない。

元と保存先の型・役割・ログ種別を照合する。端末→cloudは自端末Local→同種Drive、cloud→archiveは同種Drive→PC-A Archive。保存先の名前は元のbasenameと一致させ、新たな階層やsuffixを認めない。ファイル名の日付・対象期間の適格性は既存の対象選択が担当し、記録の形式検査で代用しない。

元/保存先の実値を含むため、本番記録は非公開のローカル原本である。Git・配布物・PRへ入れず、ログ本文、token、raw API応答、任意の例外文字列をevent_dataへ追加しない。

## イベントと判定

| 種別 | 保存する情報と参照 | 検査すること |
| --- | --- | --- |
| `prepared` | 元/保存先、コピー基準size/SHA-256、保存先内容、コピー/再利用、確認方法。先行参照なし | 元/保存先の対応と平坦化、保存先内容とコピー基準の一致 |
| `deletion_result` | 準備記録1件の参照、元/保存先、削除前の元内容、保存先内容、確認方法、要求の結果、削除後の元存在、判定・完了根拠・固定理由 | 同じrun/attemptと準備記録への結合、成功応答を記録する場合のQ5内容一致、除去確認と完了の整合 |
| `reconciliation` | 準備記録と、存在する場合は同じ準備に対する削除結果への参照。現在の元存在、保存先内容、確認方法、判定・根拠・固定理由 | 新run/attemptからの照合、同じmove/役割/対象の対応、元不在・保存先一致と照合完了の整合 |

削除要求の結果は`not_sent/succeeded/failed/unknown`、元の存在は`present/absent/unknown`として区別する。成功応答、Q5の内容一致、元の不在がそろった削除結果だけを`completed/delete_confirmed`とする。現在の元不在・保存先一致がそろった照合は`completed/reconciled`とする。元が存在するなら`incomplete`、それ以外の未確定は`unknown`とする。

削除前観測が失われた場合でも、情報を捏造せず`unknown`を保存できる。観測の欠落を成功応答・移動完了へ昇格させない。参照先の必要記録がそろわなければ、そのレコードを有効な照合記録として保存できない。完了を示す固定理由と、未完了/不明な判定を混在させない。

これらは、呼出し側が渡した観測の内部整合を検査する規則である。API/FSでの観測の真正性、削除直前性、ハンドルと実対象の結合、権限と完全な不在確認は別に必要となる。`provider_observation`等の方法名を含め、文字列だけではその保証を得られない。検査結果に元削除・回復の許可は含まれない。

## 参照と保存処理

参照は`record_id`、`<record_id>.json`という固定の相対path、保存したexact bytesのSHA-256で構成する。レコード内の任意pathを開かず、UUIDから作った直下の名前だけを読む。参照先のJSONを再整形してハッシュを計算し直すことはしない。

`save_move_record(root, raw)`は、既存記録全体、参照先、型・対象・判定を検査してから非上書き公開し、保存後もbytesと参照を読戻す。同じrun/move/attemptの準備の重複、同じ準備に対する複数の削除結果を拒否する。公開処理が失敗した場合に通常の上書き保存へ切り替えない。

`load_move_record(root, record_id)`は、参照先の実bytesと、元/保存先・move/役割/ログ種別・必要なrun/attemptの結合を検査する。参照は準備→削除結果→照合の関係に限定し、任意長の履歴鎖や循環を追い続けない。

`read_move_journal(root)`は専用ディレクトリを読み、1件でも壊れた記録、未知のentry、欠落参照、矛盾、列挙中の変更を見つければ停止する。準備記録だけが残る場合も結果から除外せず返す。部分記録や残存tmpを無視して「対象なし」にしない。未知のentryを自動削除せず、診断・回復の接続は後続で行う。

読取では通常ファイル・単一link、サイズ上限1 MiB、path/handleの前後signatureと祖先の実体を検査する。1 MiBはこの記録形式の読取上限であり、ログサイズや保存する記録件数の上限ではない。これらの観測だけで攻撃的な差替え、ACL、所有権、排他、rollback/ABA、電源断耐久性を解決したとはしない。

## 別プロセスでの検証と残件

[統合試験](../../tests/test_move_journal.py)で、合成準備/結果不明記録を保存し、別Pythonプロセスがディスクから読み直して別の照合記録を保存することを確認する。元の結果不明記録はbytes単位で保持する。子プロセスの観測値は模擬adapterからの合成値であり、実Driveへの照会や実ファイルの削除は行わない。

両経路の形式、欠落/改変参照、同じIDの内容衝突、不正な役割/対象/方法、削除応答と除去の分離、不明の保持、部分記録、試行矛盾、UTC精度も検査する。schemaを役割別パッケージへ同梱し、CIへ試験を追加する。これによって正式入口不在の配布拒否を解除しない。

この記録層単独で閉じるのは記録の外形・参照・保存/読戻しである。実状態の再観測は別の接続が必要となる。実runでの排他・private root/ACL資格、PowerShell制御との接続、実Drive adapter、経路間照合、通知/レポートへの表示、実環境受け入れは未完。Q11の実運用回復を完成としない。

続く[隔離再観測試験](cold-move-reconciliation.md)で、Windows probeの現在状態を別プロセスが読み直し、この記録へ結び付ける接続まで追加した。上記の記録層単独試験と区別し、実運用root・実Drive・正式な回復制御は引き続き未完とする。

現在の保存処理は既存記録全体も検査する。実運用件数での読取・保存性能や、所有排他の下での一括処理への接続は未検証であり、運用可能な保存性能まで受け入れ済みとはしない。
