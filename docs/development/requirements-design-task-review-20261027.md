## 2. 利用者が確認した完成像

### 2.1 解決する3つの問題（Q1回答）

1. 同一APを2端末で動かすために偏在するログを、クラウドへ自動集約する。
2. クラウド容量を圧迫しないよう、一定期間を過ぎた古いログを端末Aへarchiveする。
3. 各端末→クラウド、クラウド→端末Aの移動後に元ログを削除し、不要な重複と容量消費を減らす。

最終的にはこれらを定期実行し、以下の配置を手間なく維持する。以下のBattleLogの中間層は、利用者の「当月→各端末／当年→クラウド」を重複しない期間へ展開した整理である。

| 保持先 | BattleLog | ErrorReport |
| --- | --- | --- |
| 各端末 | 当月分 | 当年分 |
| クラウド | 当年のうち当月より前の分 | 前年分 |
| 端末A archive | 前年以前 | 前々年以前 |

2026年10月の例: 各端末は2026年10月BattleLogと2026年ErrorReport、クラウドは2026年1〜9月BattleLogと2025年ErrorReport、端末A archiveは2025年以前BattleLogと2024年以前ErrorReport。移動途中の一時的重複と、移動完了後の保持先は区別する。

### 2.2 初回完成範囲（Q2回答）

利用者は「移動完了までを最初の完成にする」を選択した。

- 手動実行で、両端末→クラウドとクラウド→端末A archiveの両経路を完了できる。
- 両経路ともコピー・保存先の内容確認・元ログ削除までを含む。コピーだけの成功を移動完了としない。
- 定期実行は、この移動部分の後に接続する。具体的な実装順・受け入れ条件・失敗時の状態はこれから設計する。
- PC-Bは自身の転送済み元ログ削除を担当する。archiveとarchive後のクラウド元ログ削除はPC-Aの経路として扱う。
- 手動実行は手動でfileを選びコピー/削除する意味ではなく、移動処理を利用者が起動する意味。入口・表示・実行手順は今後具体化する。

### 2.3 archive開始と移動完了の単位（Q3/Q4回答）

- **Q3**: PC-Bが未実行でも、クラウドにある古い分からPC-Aへ移す。Bから後日来た分は次回移す。両PCの対象期間転送完了をarchive開始条件としない。
- **Q4**: file単位で移動完了を確定する。保存先の内容確認ができたfileは元を削除し、失敗/不明なfileは元を残して結果に出し、次回その残りを処理する。対象全体のコピー成功を待って一括削除する方式は選ばない。
- したがって、あるfileの失敗や他PC未実行を理由に、他の確認済みfileの移動まで一律に未完了としない。run全体の表示は成功/部分失敗/失敗とfile別結果を区別する方向で設計し、具体的な出力形は後で決める。
- 部分完了と「失敗を成功へ隠すこと」は別。失敗file・元削除に失敗したfileの表示/次回照合条件、遅着/同名競合は設計対象に残る。

### 削除の確定要件（Q5回答）

2026-10-27、利用者は以下を削除要件として明示した。両移動経路に共通適用する。

1. **保存先の内容一致**を確認できること。
2. **削除直前の元ログがコピー時から変わっていないこと**を確認できること。
3. 上記の両方を確認できたfileだけ元を削除する。確認不能なら元を残す。

内容不一致/元の変更を観測した場合も削除可能とはしない。Q4と合わせ、該当fileは元を保持して結果へ出し、次回処理の対象として扱う。コピー/検証の成功と元削除の成功を区別し、元が残っているfileを移動完了と報告しない。

これは確認すべき事実の要件であり、常時2回のfull hash、size/更新時刻だけで十分とすること、具体的なlock/identity/API方式の採用までは決めていない。両条件を満たす確認方式を設計し、実装と受け入れ試験へ対応付ける。以下のQ5説明にある省力案は、この合意を満たすか再評価する対象であって採用済みではない。

### 2.5 移動フローの整理（2026-10-27、対話用）

利用者の「移動フローの整理から」という指示を受け、Q1〜Q5を操作の流れに展開する。以下は合意済み要件からの整理と設計提案を含む。入口の名前・実行順・再実行方式まで承認済みとはしない。

#### 2つの経路と対象

| 経路 | 実行する端末 | 元 | 保存先 | 対象期間（ファイル名の日付） |
| --- | --- | --- | --- | --- |
| 端末→クラウド | A/Bがそれぞれ実行 | 自端末のBattleLog / ErrorReport | 共通のクラウド保管領域 | BattleLogは前月末以前、ErrorReportは前年末以前 |
| クラウド→A archive | Aだけが実行 | クラウドのBattleLog / ErrorReport | Aのarchive領域 | BattleLogは前年末以前、ErrorReportは前々年末以前 |

日付判定は[既存のファイル名・期間仕様](../design/filename-and-period-selection.md)と照合した。更新時刻を日付の代用にしない。期間外の当月BattleLog/当年ErrorReportは端末に残す。クラウドではarchive対象より新しい分を残す。対象なしは変更なしとして結果に出す方向で整理する。

**Q6確認済み**: 利用者は「古いログも必ずクラウド経由にする」を選択した。初回に古いログが端末へ大量に残っている場合も、まずクラウドへ移し、archive対象ならそこからAへ移す。A自身に残る古いログにも同じ2段階を適用し、端末→A archiveの直接経路は設けない。大量転送時の容量・実行単位は別途設計する。

#### 経路1: 各端末→クラウド

1. 利用者がAまたはBで移動処理を起動する。処理は自端末の設定・対象ログを読み、期間条件に合うファイルを抽出する。
2. ファイルごとに、移動元と保存先を対応付け、コピーする元内容を確定する。保存先に同名候補がある場合は、後述の照合分岐へ進む。
3. クラウドへコピーし、クラウド側に保存された内容がコピー対象と一致することを確認する。同期フォルダへのコピー・画面上の表示だけでこの確認を済ませない。
4. 削除直前に元がコピー時から変わっていないことを確認し、Q5の2条件が成立するファイルだけ自端末の元を削除する。
5. 元削除まで確認できたファイルを移動完了として記録する。失敗/確認不能なら元を残し、未完了の理由を結果へ出す。

AとBはそれぞれの起動で進める。他端末の実行完了を待たず、BからAへのarchive操作は行わない。

#### 経路2: クラウド→端末A archive

1. 利用者がAでarchive処理を起動する。クラウドに現在存在するファイルから期間条件に合うものを抽出する。
2. ファイルごとに、クラウドの移動元とAのarchive保存先を対応付け、コピーする元内容を確定する。既存の保存先候補は照合して扱う。
3. Aのarchiveへコピーし、保存された内容がコピー対象と一致することを確認する。
4. 削除直前にクラウドの元がコピー時から変わっていないことを確認し、Q5の2条件が成立するファイルだけクラウドの元を削除する。
5. 元削除まで確認できたファイルを移動完了として記録する。失敗/確認不能ならクラウドの元を残し、未完了の理由を結果へ出す。

B未実行でも進める。Bの遅着分や今回の対象抽出後に到着したファイルは次回扱う案とする。Aで端末→クラウドの後にarchiveを起動すれば、その時点でクラウドにある古い分も対象にできる。両処理をまとめて起動する入口・必須実行順は未決であり、archive単独実行をBの実行順へ依存させない。

#### 共通の分岐と完了の見え方

| 状況 | 利用者に見える扱い | 確定/提案 |
| --- | --- | --- |
| コピー・内容確認・元不変確認・元削除が成功 | そのファイルは移動完了 | Q2/Q4/Q5から整理 |
| コピー失敗、内容不一致、元変更、確認不能 | 元を残し、そのファイルは未完了。確認済みの他ファイルは進める | Q4/Q5確認済み |
| コピー済みで元削除に失敗 | 保存先あり・元削除未了として表示。移動完了とはしない | Q2/Q4から整理 |
| 次回実行時、対応する保存先が既にある | 内容と元の現在状態を再確認し、同じコピーを増やさず残りの処理へ進む | 設計提案。照合方法・コピー時との対応付けは未決 |
| 同名で内容が異なる、候補が複数で対応不明 | 自動上書きせず元を保持し、競合として表示 | 既存の上書き禁止を維持。解消手順は未決 |
| 削除要求後に応答が途切れ、成否不明 | 完了と断定せず確認待ちにする。次回は元/保存先の現状と記録を照合 | 設計提案。元の不在だけで移動成功と推測しない |

表の項目は説明上の状態であり、新しいschemaの状態名を決めたものではない。結果は経路ごとに対象数・完了数・未完了数とファイル別理由を示す案とする。対象が抽出できなかったエラーを「対象なし」に隠さない。run全体に失敗があっても完了したファイルを取り消さず、全対象完了とも表示しない。

#### 流れを確認する受け入れ例（案）

- 2026年10月、A/Bの9月BattleLog・2025年ErrorReportがクラウドへ移り、各元は削除される。10月BattleLog・2026年ErrorReportは各端末に残る。
- 同時点でクラウドの2025年BattleLog・2024年ErrorReportをAへarchiveし、各クラウド元は削除する。2026年1〜9月BattleLog・2025年ErrorReportはクラウドに残る。
- B未実行でもAは既存の古い分をarchiveでき、後日Bから到着した分は次回archiveできる。
- 複数ファイルのうち1件の確認が失敗した場合、その元だけ残る。別の確認済みファイルは元削除まで進み、結果は部分完了となる。
- コピー後の元変更・削除失敗・応答途絶後の再実行を区別し、内容喪失や不要な重複を生まず残りを完了できることを具体設計後に試験する。

#### 既存仕様への反映待ち

期間境界・ファイル名検証・同名異内容の上書き禁止は既存仕様と一致する。一方、[ファイル名・期間仕様](../design/filename-and-period-selection.md)§4/6/7のcopy-onlyと全体archive待機、[runtime gate](../design/runtime-entrypoint-validation-gate.md)§2/3の両PC証拠待ちはQ2〜Q4と整合しない。既存の詳細契約と状態遷移を再照合する際に改訂する。過去の全体成功manifestだけで現在のファイル移動を承認する方式には置き換えない。

### 2.6 保存先の構成（Q7回答、2026-10-27）

利用者の「保存先の構成から」を受け、[READMEの保存先](../../README.md#pcごとの役割と実行パス)、[Aの公開設定例](../../Config/PC-A.example.json)、[Bの公開設定例](../../Config/PC-B.example.json)、[ローカル管理領域の設計](../design/configuration-local-root.md)と照合した。利用者は**「ログ種別ごとの共通フォルダに集約する」**を選択した。クラウド・AのarchiveともPC別のサブフォルダは設けず、新しい年別フォルダの追加もひとまず行わない。

#### 保存先の見え方（確定した構成）

以下は論理構成であり、実運用パスではない。配下のファイル例は公開用のダミー。

```text
クラウドの共通保管領域/
  BattleLog/                ← A/BのBattleLogを集約
    20260901_12000000@sample.txt
  ErrorReport/              ← A/BのErrorReportを集約
    20250101_12000000.txt
  _maintenance/             ← ログ以外の管理記録（既存設計）

端末Aのアーカイブ領域/
  BattleLog/                ← クラウドから移した古いBattleLog
    20250101_12000000@sample.txt
  ErrorReport/              ← クラウドから移した古いErrorReport
    20240101_12000000.txt
```

| 元 | 保存先 | 設定との対応 |
| --- | --- | --- |
| A/BそれぞれのBattleLog | 共通クラウドのBattleLog | 各PCの`battleLogLocal` → `battleLogDrive` |
| A/BそれぞれのErrorReport | 共通クラウドのErrorReport | 各PCの`errorLogLocal` → `errorLogDrive` |
| 共通クラウドのBattleLog | AのarchiveのBattleLog | Aの`battleLogDrive` → `battleLogArchive` |
| 共通クラウドのErrorReport | AのarchiveのErrorReport | Aの`errorLogDrive` → `errorLogArchive` |

A/BでDrive上のローカル表示パスが異なっても、クラウド上では同じログ種別の保管先を指すことが必要。パス文字列の一致だけで同じ保存先と判断する設計にはしない。クラウドの対象識別方法は詳細契約で具体化する。

端末Aのarchiveは通常のログ出力先と区別する。Bにはarchive保存先を持たせない。ログと管理記録を分け、各PCの管理記録のローカル原本は既存の`maintenanceLocal`へ置く。管理記録の詳しい配下構成・クラウド複製の扱いは今回変更していない。

#### ファイル名・サブフォルダと競合の境界

- PC名や実行日時をファイル名へ付け足す方式は今回採用していない。ログを探すための配置と、転送元を示す管理記録は分けて設計する。
- 年月はファイル名から判定できるため、保存先に新しく年/月の分類階層を作ることは初回構成に含めない。
- **追加指示で確定**: 元に既存のサブフォルダがあっても階層は保持せず、対象ログをファイル単位でログ種別ごとの共通フォルダ直下へ集約する。端末→クラウド、クラウド→A archiveの両経路に適用する。前回の相対階層保持案は採用しない。対象期間・ファイル名の検証は引き続き適用する。
- 保存先の候補は「ログ種別の保存先ルート＋元ファイル名」となる。同じ端末内の異なるサブフォルダからも、A/Bからも同名ファイルが来得る。内容が同じ場合の共用・再利用と、異なる場合の競合解消は次の論点。平坦化から自動重複排除・改名・上書きの許可を導かない。異内容の自動上書き禁止は維持する。
- 同名競合の確認には、A/B間だけでなく、既にクラウドやarchiveにあるファイルと、後日届いた古いファイルも含める。

例: Aの`BattleLog/old/20250901_12000000@sample.txt`はクラウドの`BattleLog/20250901_12000000@sample.txt`へ、クラウドの`BattleLog/old/20250901_12000000@sample.txt`はA archiveの`BattleLog/20250901_12000000@sample.txt`へ移す。どちらも`old/`は再現しない。元ファイルの識別・削除対象の特定には元の相対パス等を保持し、保存先の名前だけから元を推測しない。記録形式は詳細設計で具体化する。

この合意はログファイルの保存先構成に関するもの。管理記録のフォルダ構成は変更せず、元の空フォルダ削除も要件に追加しない。

保存先ルートの大枠は現行の設定例と一致するが、元の相対パスと保存先パスの対応は平坦化に合わせた設計・既存契約の照合が必要。設定/schema/コードは変更していない。既存データの再配置・フォルダ作成・本番接続も行っていない。次はこの共有構成を前提に、同名同内容・同名異内容・保存済みで元だけ残った場合を整理する。

### 2.7 同名ファイルの扱い（Q8回答、2026-10-27）

利用者の「同名ファイルの扱いを整理」を受け、[既存の重複・競合規則](implementation-workflow.md#24-collision-and-duplicate-handling)、[Drive内容比較](../design/drive-content-comparison.md)、[PS/Pythonの責務](../design/powershell-python-contract.md)を照合した。利用者はQ8で**「異内容は元を残して競合表示する」**を選択した。同内容の保存先再利用という提示内容と合わせて両経路へ適用する。以下の一括発見/同時実行・記録形式の詳細は設計案として区別する。

#### 判定と処理案

比較範囲はログ種別ごとの共通保存先。同一PCの別サブフォルダ、A/B間、過去の実行、遅着分のいずれから生じた同名も同じ基準で扱う。BattleLogとErrorReportは保存先が別なので、ログ種別をまたぐ同名は衝突としない。

| 保存先の状況 | 扱いの案 | 元ログ |
| --- | --- | --- |
| 同名ファイルなし | 通常どおりコピー・内容確認・元不変確認へ進む | Q5の2条件成立後に削除 |
| 同名ファイルが1件で内容一致を確認できる | 保存先を再利用し、再コピーや別名コピーを増やさない | コピー時に相当する今回の比較対象内容を確定し、Q5の2条件を確認できた元だけ削除 |
| 同名ファイルがあり内容が異なる | 初回完成では既存の保存先を変更せず、該当元を競合として報告する（Q8確定） | 削除せず残す |
| 内容一致を確認できない・保存先を特定できない | 保留として理由を表示する | 削除せず残す |
| クラウド上に同名候補が複数あり、対応先が一意に決まらない | 自動で選ばず保留。重複候補の整理は別途扱う | 削除せず残す |

「同内容」はファイル全体の内容一致であり、名前・サイズ・更新時刻の一致だけで判定しない。コピーを省略する場合も、過去の成功記録だけに頼らず現在の保存先と今回の元を確認する。具体的な比較方式、確認から削除までの対象の結び付けは詳細設計で決める。

#### 同じ名前を持つ複数の元ファイル

- 同内容なら保存先は1ファイルを再利用する案とする。ただし元はそれぞれ別の処理対象として記録し、各元の不変確認・削除結果を個別に確定する。1件の一致確認から同名の元をまとめて削除しない。
- 異内容なら後から来た内容で保存先を上書きしない。元のPCや階層だけを理由に優先順位を付けず、内容を連結・マージしない。
- 保存先が空の時点で同名異内容の元を複数発見した場合も、列挙順で一方を正本と決めない。事前に分かる衝突はグループとして報告し、異内容を保留する案。別のPC/実行が先に保存した後に衝突が分かった場合は、その保存済みファイルを変更せず、今回の異内容の元を残す。
- 処理中に別の実行が同名を作成した場合は、その保存先を再照合する。事前に空だったという理由で上書きしない。具体的な同時実行制御は未設計。

#### 元削除だけが残った場合との接続

コピー成功後に元削除が失敗した場合、次回は「同名・同内容の保存先あり」として確認し直す案とする。保存先を再利用できても、元が変わっていれば削除せず残す。元の不在や保存先名だけから過去の移動成功を推測しない。元相対パス/クラウドの対象識別子等と、保存先の対応・内容・個別結果を記録する設計が必要。

#### 既存の別名保存案との関係・Q8

既存の実装計画§2.4には、異内容を`_PCA`/`_PCB`付きの名前で両方保存し、出所不明や別名の再衝突は保留する方針がある。今回の平坦化では同一PC内の別階層でも同名異内容が生じるため、PC名だけでは区別できない。既存の別名規則をそのまま適用して全件を自動解決できるとはしない。

**Q8（確認済み）**: 同内容なら保存先を再利用する整理を前提に、利用者は異内容を元保全・競合表示とする方針を選択した。既存の自動別名保存方針をこの範囲で変更し、実装計画§2.4へ反映した。初回完成では自動suffix付与・既存ファイルの改名・異内容の上書き/マージを行わない。競合は放置しても自動解決せず、該当元の容量削減も未完となる点を結果に出す。手動解消の具体手順と、将来の自動別名保存の採否は未決。既存のsuffix付きファイルを自動で元名へ戻したり削除したりする指示ではない。

受け入れ例（案）: 同名同内容を複数元から処理して保存先1件と各元の個別完了を確認する。同名異内容・内容不明・複数候補で上書き/元削除をしない。同名異内容は自動改名せず元を残し競合を表示し、無関係なファイルは処理できる。元変更や削除失敗を経た再実行でも内容喪失やコピーの増殖を起こさない。

### 2.8 失敗・中断後の再実行（Q9回答、2026-10-27）

利用者の「次の整理」を受け、[API試行の契約](../design/powershell-python-contract.md)、[正式入口の復旧条件](../design/runtime-entrypoint-validation-gate.md)、[明示回復コマンド](../design/explicit-recovery-command-design.md)と照合した。Q4/Q5/Q8を再実行時の利用の流れへ展開する。利用者はQ9で**「同じ移動処理の再実行で残りを進める」**を選択した。通常失敗後の操作は確定し、結果不明の確定方法・記録形式等は詳細設計対象として残す。強制終了からの自動回復を追加する合意ではない。

#### 利用者の操作と処理の流れ（Q9確認済み）

1. 通常のファイル失敗や元削除失敗は、原因を解消した後、同じ経路の移動処理をもう一度起動する。利用者がファイルを選び直したり、元を手動で一括削除したりする操作を前提にしない。
2. 新しい実行として現在の対象期間・元・保存先を確認する。前回の失敗ファイルだけに固定せず、新たな対象や遅着分も扱う。過去の完了記録は書き換えない。
3. 残っている元について、保存先がなければコピー、同名同内容があれば再利用、異内容/確認不能なら保留とする。削除直前の2条件は今回もファイルごとに確認する。
4. 今回完了した分、競合/確認不能で残った分、前回の結果不明で照合待ちの分を区別して結果へ出す。

#### 再実行で確認する状態

| 状況 | 次の扱い | 根拠/未決 |
| --- | --- | --- |
| 元があり、保存先なし。前回コピー未完了 | 元の現在内容を対象として新たにコピー・検証する | Q4/Q5。前回の一時ファイルを完成品にしない |
| 元があり、保存先に同内容あり。前回元削除失敗 | 保存先を再利用し、今回の比較対象内容と元不変を確認して元削除を進める | Q5/Q8。前回の確認済みフラグだけで削除しない |
| 元が前回コピー後に変わった | 前回内容に基づく削除をしない。次回は現在内容を改めて評価する | 同名の保存先と異内容ならQ8により競合。永久に前回内容へ固定しない |
| コピー要求後に通信断・応答途絶 | 保存先の現在状態を調べてからコピー/再利用/保留を判断する | 既存の結果不明upload照合。盲目的な再送で増殖させない |
| 元削除要求後に応答途絶 | 元の現状と保存先内容、当該操作の記録を照合する | 元があれば今回のQ5確認へ。元の不在だけで完了としない。確定方法は詳細設計 |
| 元なし、保存先あり、前回の結果不明が残る | 前回の元/保存先の対応・内容・操作記録で確認し、十分な根拠がなければ照合待ち | 過去の不明を、今回の対象0件という表示で消さない |
| 元も保存先も確認できない | 完了にせず所在未確認として表示する | 自動復元・別ファイルの削除へ進まない |
| 同名異内容、対応先が複数、比較失敗 | 元を残して競合/確認不能を表示する | Q5/Q8。実行回数を増やしても未解消なら保留のまま |

保存先が次の経路でAへarchive済みの場合も、クラウドの不在だけで前段の移動成功/失敗を推測しない。両経路の記録の対応付けで確認する方式は詳細設計対象とする。

#### 通常の失敗と実行全体の中断

- ファイル単位の読取/比較/削除失敗は、依存しない他のファイルを進められる範囲で部分完了とする（Q4）。認証・保存先の識別・設定・排他など共通の前提が成立しない場合は、影響する経路を止める。対象を調べられない状態を「対象なし」にしない。
- API呼出し内の一時的エラー再試行と、利用者が後日起動する再実行は別。既存のPowerShell管理・初回込み最大4回/待機1・5・15分という値を今回変更しない。認証/権限/競合を、原因未解消のまま繰り返す設計にしない。新しい削除操作のretryable分類・結果照合方法は未設計。
- 強制終了・PC再起動・電源断により実行中記録/所有権の問題が残る場合は、既存の明示回復設計へつなぐ。古いという理由でロックや一時ファイルを消し、通常処理を強行しない。通常の起動時に回復が必要と分かれば停止して案内する。回復入口の実装・状態変更は未完のまま。
- 一時ファイル/未完成コピーは完成した保存先と区別する。再利用/片付けは所有権と内容の確認方法を設計してから扱い、利用者へログ全体の削除や作業領域の一括消去を要求しない。

#### 完成を確認する例（案）

1. 3件中2件完了・1件コピー失敗の後、同じ操作を起動すると残る1件と新規対象を処理し、完了済みのコピーを増やさない。
2. コピー成功・元削除失敗の後、同じ操作で保存先を再利用し、元削除まで進める。途中で元が変わっていればその元は残す。
3. コピー/削除の応答途絶では、現在の状態と記録を照合するまで再送/完了判定をしない。根拠不足なら結果不明を表示する。
4. 強制終了後は回復要否を表示し、ロックの自動破棄や過去のrunning記録の成功化を行わない。

**Q9（確認済み）**: 通常のファイル失敗・元削除失敗の後は、同じ移動処理を再実行して現在の状態から残りを進める。通常失敗のための専用再実行操作は必須にしない。競合/確認不能分は元を保持して表示し、保存済みの同内容は再利用する。強制終了時の明示回復条件は解除しない。実装計画へこの操作方針を反映した。

### 2.9 競合の確認・解消と結果表示（Q10回答、2026-10-27）

利用者の「次の整理」を受け、Q8の異内容保留とQ9の通常再実行を、結果の確認から次の操作までの流れへ展開する。[既存の重複/競合規則](implementation-workflow.md#24-collision-and-duplicate-handling)、[ファイル名規則](../design/filename-and-period-selection.md)、[manifest/run状態](../design/staging-file-lifecycle.md#8-manifest-and-run-status)と照合した。利用者はQ10で**「概要・詳細レポートと通常再実行までにする」**を選択。初回の支援範囲は確定し、専用の比較・解消ツールは後続候補とする。以下の表示名・項目は設計案であり、schemaや終了コードを決めたものではない。

#### 競合があるときの利用の流れ（初回支援範囲はQ10確認済み）

1. 移動処理は該当元を残して競合と記録し、依存しないファイルを処理する。既存の保存先は改名/上書き/削除しない（Q8）。
2. 実行後の概要に未完了件数と主な理由を表示し、ローカル詳細レポートの確認先を案内する。
3. 利用者が同名の元と保存先、内容比較の結果を確認し、どの内容を残す必要があるか判断する。プログラムは不要な方を推測せず、「保存先を消せばよい」「元を消せばよい」と一律の削除手順を示さない。
4. 解消した後に同じ移動処理を起動し、現在の状態で再判定する（Q9）。前回レポートへの確認済みチェックや編集を、元削除の許可にしない。

両方の異なる内容を同じ共通フォルダへ残すには、平坦化と両立する別名規則が必要。初回は自動別名保存を採用していないため、単純に`_PCA`/`_PCB`や連番を付ける解消手順も提供しない。特にErrorReportは既存のファイル名規則に反し得る。具体的な両内容保管・手動解消の手順は別途設計し、未解消の競合は容量削減未完として残る。

#### 実行後の概要表示（案）

| 表示上の結果 | 意味 | 次の行動 |
| --- | --- | --- |
| 完了 | 今回の対象が元削除まで完了し、未解決の不明/エラーもない | 通常運用へ戻る |
| 対象なし | 列挙・期間判定が正常に終わり、今回の対象も照合待ちもない | 次回実行を待つ |
| 部分完了 | 完了した分と、未完了/競合/確認不能が残る | 理由を確認して通常再実行 |
| 未完了 | 対象はあるが移動完了した分がない | 原因を確認する |
| 処理停止・回復確認が必要 | 設定/認証/対象識別/排他などの前提が満たせず、処理を進められない | 原因対応または明示回復手順へ |

上記は利用者向けの説明であり、新しいrun status enumではない。既存の`success`/`partial_failure`/`failure`等との対応は、削除を含む契約の改訂時に設計する。対象なしは既存の`success`＋`outcome: no_work`と照合し、別の`skipped`状態を増設しない。過去の結果不明が未照合なら、今回の元が0件でも「問題なく対象なし」としない。

経路・実行端末・対象期間・開始/終了・対象数・移動完了数・未完了数を概要へ出す案。完了数はコピー件数ではなく元削除まで確認できた元ファイル数。平坦化で同内容の元3件が保存先1件を共用しても、元3件の完了と保存先1件を混同しない。理由別内訳は元ごとの主理由で重複計上せず、過去の照合待ちは今回対象と分けて表示する。

#### ローカル詳細レポート（案）

| 情報 | 用途 |
| --- | --- |
| 経路・元端末・ログ種別・元の相対パス | 同一PC内の別サブフォルダにある同名の元を区別する |
| 保存先の論理位置/ファイル名と対象を特定する参照 | 比較・保留した相手を取り違えない。表示名と内部identityは区別する |
| コピー/保存先確認/元不変確認/元削除の結果 | コピーだけ済んだのか、削除まで済んだのかを示す |
| 未完了の理由・確認時点 | 異内容、元変更、削除失敗、結果不明、権限不足等を区別する |
| 比較の根拠となるサイズ・内容指紋と、その取得可否 | 異内容と未確認を区別する。指紋一致だけで処理全体完了とはしない |
| 次の行動 | 通常再実行、競合内容の確認、認証/権限の対応、回復確認等を案内する |

レポートは各PCのローカル管理領域で扱う案とし、実ログ本文・秘密・raw API応答/例外を載せない。通常画面や共有可能な診断には固定理由と安全な参照を使い、必要な実対象の確認はローカルの詳細と区別する。実値をGit/PR/公開例へ追加しない。保存形式・ファイル名・保持期間・参照の表示方式は未決であり、比較/解消ツールを実装済みとはしない。

レポート保存に失敗した場合は保存失敗を表示し、実際の移動済みファイルと結果記録の失敗を区別する。既に行った元削除を取り消したり、記録成功を装ったりしない。削除前の必要記録と、実行後の利用者向けレポートの関係は詳細設計対象。

**Q10（確認済み）**: 初回の競合対応は「概要＋ローカル詳細レポート、利用者の判断、解消後の通常再実行」までとする。自動解消は行わず、専用の比較・解消ツールは後続候補とする。実装計画へ範囲を反映した。ローカルレポートの具体形式・保持期間・表示項目/状態対応、両内容を残す手動解消手順等の詳細まで確定したとはしない。

受け入れ例（案）: 同一名・別階層の元を区別して表示する。コピー済み/元削除未了を完了数に含めない。競合を残しつつ他の完了分を示す。対象列挙失敗や過去の結果不明を対象なしに隠さない。レポート出力失敗・秘匿項目の非出力も確認する。

**Q5（確認済み）**: 削除の最低条件を「保存先の内容一致を確認し、削除直前にも移動元がコピー対象から変わっていないことを確認できたfileだけ。どちらか不明なら元を残す」とする。

経緯: 利用者は保存先の内容一致だけで足りるのではないかと質問し、以下の懸念・比較時点・省力案を説明した後、2条件を両方確認し、確認不能なら元を残す要件を明示した。最終回答は上記および§2の確定要件に反映した。

#### 内容一致の比較時点と懸念（rootの説明・提案、未合意）

| 保存先の確認方法 | 元が途中で変わった場合 |
| --- | --- |
| コピー時に読んだ元内容と保存先が一致 | コピーの正しさは分かるが、その後の元の追記/差替えは分からない |
| 削除直前の元内容と保存先が一致 | 元が変わっていないことの確認を、この内容比較に含められる。別のfull hash検査を重ねる必要はない。ただし確認と削除の間の変更可能性は別に残る |

例: 元の内容Aをコピーし保存先Aの一致を確認した後、元へBが追記される。元の現在内容A+Bをそのまま削除すると、保存先にないBを失う。同じpathの元fileが別内容へ差し替えられた場合も同様。端末→クラウド、クラウド→PC-Aの両経路で、保存先がコピー時snapshotと一致していても起こり得る種類の問題である。

対象は過去月/過去年のログなので通常の追記頻度は低いという想定は可能だが、アプリ/手作業/他端末から処理中に変更されないことは未確認。実ログで発生を確認したという主張ではない。元内容を処理中固定できる前提や方式が成立するなら、独立した再確認を省ける場合もある。

説明時の省力案は、コピー前に記録した元のsize/更新時刻等が削除直前に変わっていれば元を残して次回処理する、という軽い変更検出だった。metadata一致だけでは全ての変更を検出できず、確認と削除も原子的にはならない。この方式の十分性・採用は未決であり、Q5の2条件合意からmetadataだけの採用を導かない。新しいhelperや複雑な排他方式をこの段階で自動追加しない。

内容確認案: 端末→クラウドはクラウド実体のsize/SHA-256、クラウド→PC-Aは保存後に読み直したsize/SHA-256。Drive for desktop上の表示だけでクラウド完了としない。照合API・移動元identityの具体方式・失敗時の扱いは、この最低条件の確認後に設計する。

Q1〜Q5回答は§2へ反映済み。次は同名競合・コピー済み/削除未了の再実行等を既存仕様と照合する。未決の削除API方式を、これらの回答から推測して確定しない。
