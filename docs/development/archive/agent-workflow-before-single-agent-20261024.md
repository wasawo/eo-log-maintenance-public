# 役割別エージェントの運用

全担当が [AGENTS.md](../../../AGENTS.md) を守る。既存の二層構成（恒久規則/変動進捗）を維持し、役割設定と必要時の作業スキルを追加する。役割への割当は利用者の承認範囲を広げない。

## 役割と設定

| 担当 | 成果物 | 設定・既定モデル/思考量 |
| --- | --- | --- |
|ルート| 作業指示、判断事項、統合差分、PR/CI状態、handoff | メインモデルは維持。推奨 `gpt-6.1-sol`。プロジェクト既定は [config.toml](../../../.codex/config.toml) の `medium` |
|アナリスト| 根拠ファイル/行付き要件、対象範囲、受け入れ条件、矛盾・未決定 | [analyst.toml](agents-20261024/analyst.toml): `gpt-6-luna` / `medium` |
|実装者| 割当範囲のコード・テスト・関連仕様、自己検証結果、残課題 | [implementer.toml](agents-20261024/implementer.toml): `gpt-6.1-sol` / `low` |
|レビュー担当者| 重大度・根拠行・再現条件付き指摘、条件別の確認結果、未検証範囲 | [reviewer.toml](agents-20261024/reviewer.toml): `gpt-6.1-sol` / `medium` |

2026-10-24の利用者指示で思考量を低減し、モデルは維持した。`root.toml`は作らない。rootの既定はプロジェクトconfigで設定するが、信頼済みプロジェクトでのみ読み込まれ、明示的な起動/クライアント設定が優先され得る。現在の会話の思考量をこのファイルだけで変更済みとは扱わない。次回読込後の実効値を確認する。

通常は上記既定を使い、複数ファイルの意味論的変更はimplementerを `medium` にする。排他・原子的更新・クラッシュ復旧・ACL・不明Drive結果など、失敗時にデータ/権限へ影響する変更の設計・独立レビューだけ `high` を検討し、理由と対象を限定する。単純な文書・参照変更では引き上げない。カスタムファイルの値が優先される環境では必要な担当設定だけを一時変更し、作業後に既定へ戻す。モデルが利用できない場合は代替と影響を明示する。

## 開始と受け渡し

1. rootがhandoffと実Git/GitHub状態を確認し、目的、基準SHA、対象/編集許可ファイル、承認済み条件、根拠仕様、受け入れ条件、操作権限を渡す。小さな文書修正などはrootだけで処理してよい。
2. analystが対象を調査し、事実・推測・未決定を分ける。rootが実装範囲を確定し、利用者判断が必要ならその依存部分を保留する。
3. implementerが確定した範囲を編集し、対象検証を実施する。仕様変更が必要になったら独自確定せずrootへ戻す。
4. reviewerが根拠仕様と対象差分から独立に確認する。実装者の説明だけで判定せず、不足する負例・安全条件・テスト範囲を確認する。
5. 指摘修正はimplementerへ返し、修正差分を再確認する。rootが全体整合・検証・handoffを確認し、利用者の指示範囲でコミット/PR/CI/マージを行う。

analyst/reviewerは追跡ファイルを編集しない。reviewerのテストは隔離した合成領域を使う。Git/PRの変更とhandoff更新はrootのみ。共有作業ツリーでは同じファイルの並行編集を禁止し、検証中にも対象差分を変更しない。外部作業ツリーを使う場合も担当と統合責任を明確にする。

## 読込量と報告量

- 共通AGENTSと必要な役割指示は全担当が読む。root以外はhandoff全体、全仕様、会話履歴を毎回読む必要はない。対象の承認条件と参照先を渡し、不足する根拠は直接確認させる。
- 常時3体を起動しない。rootを含め最大4担当とし、下位担当からの追加委譲は行わない。独立した調査は並行化できるが、設計確定前の依存実装や編集中のレビューは避ける。
- 利用者が既存担当のみ・新規作成禁止を指定した場合、既存のanalyst/implementer/reviewerだけを再利用し、別名の個体の起動や新規作成を行わない。指定担当が存在しない場合はrootが処理し、独立レビュー未実施を記録する。
- 最終報告は対象/基準、根拠、変更・指摘、検証、未確認/判断待ちへ絞る。raw logや実値を貼らない。
- 複数担当は重複読取・受け渡しで総トークンを増やす場合がある。モデル分担だけで消費削減を保証しない。
- 調査済み条件が揃った小変更はrootで編集し、必要ならreviewerだけを起動する。analyst→implementer→reviewerを毎回必須にしない。差分・根拠の必要箇所だけを渡し、同じ確認や長い出力を重複させない。独立レビューや必要なテストを消費削減のために省略しない。

## 設定の適用と確認

プロジェクトのカスタム担当は `.codex/agents/*.toml`、スキルは `.agents/skills/*/SKILL.md` に置く。個人用のグローバル設定や外部プロバイダーは変更しない。役割の読取専用指示は作業規則であり、OSの書込権限を独立に隔離する保証ではない。

通常はカスタム担当を名前で指定する。実行環境がカスタム定義を起動機能へ直接公開しない場合、rootが該当TOMLを読み、モデル・思考量・指示を明示して起動する。必要最小限の引き継ぎを使い、別モデル起動で履歴継承が使えない環境では履歴なしの起動に根拠ファイルと条件を渡す。

設定ファイルを作っただけで稼働確認済みとはしない。次のセッションでプロジェクトが認識されていること、担当/スキルの検出、選択モデル・思考量を確認する。認識されない場合は再読込/再起動後に確認し、実際に使ったモデルと差異を報告する。
