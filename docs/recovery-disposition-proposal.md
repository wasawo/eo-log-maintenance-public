# stale lock の明示的回復フロー案

状態: 利用者判断待ち。実装・本番操作を許可する決定書ではない。
根拠: [承認済みOSD-02 C2/C3](osd-02-crash-concurrency-options.md)、[所有権/復旧ゲート](lock-recovery-acceptance-gate.md)。

## 判断が必要な点

C2/C3は、旧ownerの終了確認・別のdisposition記録・新run/fresh inventoryを要求する。
ただし、利用者が回復を開始する入口、旧lockの扱い、記録形式と保管先は未確定。
現行acquire_owned_lockはabandoned mutexでも既存lockでも停止し、回復判定が肯定でもその挙動は変わらない。

## 推奨する入口

通常の同期実行では回復を自動開始しない。専用の明示的な回復コマンドを別途設計する。
最初は読み取り専用の診断・計画表示を既定とし、状態変更は別の明示操作とする。
通常の同期がstaleらしいlockを発見した場合は、秘匿化した理由と回復手順への案内を示して停止する。
この案への承認は入口方針の承認であり、正式ランタイム導入や本番適用の承認ではない。

## 実装前に満たす条件

- 回復中も同じscopeのOS mutexを保持し、scope/host/recordの厳密な検証と信頼できる旧owner終了証拠を要求する。PID・経過時間・host名・abandoned通知だけで終了や引継ぎを断定しない。
- abandoned通知は取得後に失われ得るため、再起動後の回復をその通知だけで判定しない。永続的なowner/process identityと終了証拠の契約は別途具体化する。
- 最新manifestは完全な列挙と検証済みbytesで選択し、Drive結果不明は照合が完了するまで保留する。旧running manifest・staging・元ログ・Drive・archiveは変更しない。
- 旧lockの元bytesを非公開の管理証拠として保存し、公開向け診断にはtoken/host/実パスを出さない。dispositionのschema・保存領域・権限・保持期間は別途レビューする。
- 旧recordの扱いは、検証した対象だけに作用する手段を確立するまで実装しない。単なるpath再読取後unlinkは競合に対する証明にならない。安全な手段がなければ停止する。
- 途中失敗・再実行・別プロセス競合で記録を上書きせず、診断証拠を保持する。回復中断を再現する合成テストを先に定義する。
- 回復後は新token・新run_idと新しいsource inventory/per-file stateを使う。旧statusの転記・旧manifestの終端化は行わない。
- 全安全ゲートの受け入れまで正式同期/アーカイブ入口へ接続しない。PC-Bにarchive/deletionを追加しない。

## 比較する選択肢

1. 推奨: 専用の明示的回復コマンドを設計する。通常同期は停止を維持する。
2. 回復コマンドも当面追加せず、診断・運用手順の文書化にとどめる。

いずれも「旧lockを手で削除すればよい」という手順は承認しない。
この判断前に可能な最新選択と復旧分類の合成接続検証は実施済み。
方式確定後も、残る証拠形式・安全な状態遷移・FS/実運用受け入れを完了扱いしない。
